# Audit: aletheia-boundary 0.0.3 (2026-10-29)

**Scope:** every file at commit `23f80da` (2,098 lines), read in full; build, unit
and integration tests run; adversarial attacks run by an agent using only
`boundary_request` inputs.

**Environment:** Linux, Node 22.23.4, npm 10.9.9, PostgreSQL 16.15 (local
server, loaded with `scripts/init-readonly.sql`, SCRAM password auth, port
5434). Docker was not available, so `docker-compose.yml` itself was not run; the
database it describes was reproduced by hand.

**Original verdict (0.0.3):** the write side holds. The read side, the receipts and the
fail-closed claims do not. Do not put this in front of real data until
F1 to F6 are closed.

## What was claimed and what is true (at 0.0.3)

| 0.0.3 claim | Result |
|---|---|
| The 10 integration assertions pass against real Postgres | **True.** All 10 pass on PostgreSQL 16.15. |
| `npm install` then run | **False.** A fresh `npm install` fails: `prepare` runs `tsc`, which errors on `pg-cursor` (no type declarations). |
| Smoke test (`npm test`) | **Cannot fail.** It uses `console.assert`, which prints and exits 0. |
| "Raw data never leaves the customer boundary" / policy enforcement | **False for `query`/`export`.** See F1. |
| "Tamper-evident log, vendor cannot rewrite history" | **False.** See F2. |
| "Fail-closed by default" | **False in three places.** See F3, F4, F5. |
| "Writes impossible" | **True.** The role probe refuses writable roles, and a `set_config` attempt to leave the read-only transaction was rejected by Postgres; the write canary stayed empty. |

## Findings (original)

Severity: **Critical** releases forbidden data or forges evidence. **High**
breaks a stated guarantee. **Medium** weakens assurance or agent usability.

| ID | Severity | Finding | Evidence |
|---|---|---|---|
| F1 | Critical | Policy is evaluated against the agent-supplied `resource` label, but `query`/`export` run arbitrary `params.sql` that is never tied to that label. Column allowlists and redaction match result column *names*, so aliases (`ssn AS value`) and `row_to_json(u)::text AS value` pass them. | `audit/attacks.ts` A1, A2, A3: SSNs and emails from `public.users` released under the shipped `example.yaml` and under the integration test's own policy. Integration assertion 7 itself queries `public.analytics_daily` under label `analytics`. |
| F2 | Critical | Receipt `contentHash` does not cover the request or the decision. `canonical()` passes `Object.keys(obj).sort()` as a `JSON.stringify` replacer, which whitelists those *top-level* key names at every depth, so nested `request`/`decision`/`payloadSummary` fields are dropped. No code ever recomputes a hash from the body; the integration test checks only `prevHash` links and the signature over the stored hash. | A6: decision changed `deny`→`allow`, reason and resource rewritten; hash unchanged, signature valid. |
| F3 | Critical | If the Postgres provider fails to start, including when the read-only probe **refuses a writable role**, the MCP server falls back to `StubProvider` and serves fake rows with `ok: true` and a signed receipt. The agent cannot tell. | MCP client run with the `writable` role: stderr says "Refusing to start", tool returns `ok=True` with stub data. |
| F4 | High | Any `effect` other than the exact string `deny` is treated as allow. A typo releases data. `zod` is a dependency but policies are not validated. | A5: `effect: "denny"` released all of `public.users`. |
| F5 | High | Constraint types `aggregate` and `rows` are accepted by the schema but not implemented. A rule using them releases unconstrained rows, and records `transforms: none`. | A4: `aggregate: count` released raw rows with SSNs. |
| F6 | High | The log is never verified. On startup, corrupt lines are skipped silently and the chain/signatures are not checked. There is no verify command, so a customer cannot audit the log. | `src/receipt/log.ts` `hydrateFromDisk`. |
| F7 | High | Build is broken on a fresh clone (`pg-cursor` types), and `package-lock.json` is not committed, so installs are not reproducible. | `npm install` exit non-zero; `tsc --noEmit` error TS7016. |
| F8 | High | The unit smoke test cannot fail (`console.assert`). There is no test runner and no CI. | `node -e 'console.assert(false)'` exits 0. |
| F9 | Medium | Output to the agent is bounded only by `maxRows` (default 10,000). A rule without a `limit` can return up to 10,000 rows in one tool result. | `src/data/postgres.ts` `readLimited`. |
| F10 | Medium | `schema` with resource `*` returns column names of every table, including ones the policy denies (`users.ssn`). Metadata, not data, but it tells an agent where to aim. | `example.yaml` `allow-schema` + `execute` `schema` case. |
| F11 | Medium | MCP server reports version `0.0.2`; package is `0.0.3`. A policy load failure falls back to deny-all (correct) but the agent only sees denials, not why. | `src/mcp/server.ts` lines 38, 85. |

## What held (0.0.3)

- Read-only role probe refuses a writable role (assertion 2 and the MCP run).
- `BEGIN TRANSACTION READ ONLY` + rollback: `set_config('transaction_read_only','off',true)` was rejected by Postgres (A7); the write canary stayed empty.
- Multi-statement and listed dangerous functions are blocked by the classifier (superseded by structured-only path in 0.0.7).
- Parameter values go through `pg` bind parameters, not string concatenation.
- Deny decisions reach the agent with `isError: true` and a reason.

## Reproduce (historical 0.0.3)

```bash
npm install --ignore-scripts        # plain `npm install` fails, see F7
# Postgres 16 with scripts/init-readonly.sql on localhost:5434 (docker compose up -d)
export DATABASE_URL=postgres://readonly:readonly@localhost:5434/boundary
export DATABASE_URL_WRITABLE=postgres://writable:writable@localhost:5434/boundary
npm run test:integration             # 10/10 pass
npx tsx audit/attacks.ts             # 6 LEAK, 1 HELD; exits 1 until fixed
```
